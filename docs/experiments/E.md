# Эксперимент E — синхронный `scan_folder` на UI-потоке

## Гипотеза

`gallery::scan_folder`, вызванный синхронно на UI-потоке winit
(`main.rs:815` в `open_dropped_path`, а также `main.rs:825` для открытого
файла), на папках из 1k/10k файлов превышает гейт **100 мс до первого кадра**
(`docs/GALLERY_ARCHITECTURE.md`, гейт «first catalog row, 1k entries |
≤100 ms warm / ≤250 ms cold», таблица §8).

## Метод

Бенчмарк `crates/rrrah-app/benches/folder_scan.rs` (custom harness, по образцу
`prefetch_scheduler`). Прогон: `cargo bench -p rrrah --bench folder_scan`.

- Синтетические папки: 1 000 и 10 000 поддерживаемых файлов (`.CR3`/`.DNG`,
  регистр расширений перемешан) + 25 % «мусорных» сайдкаров (`.JPG`/`.XMP`/
  `.TXT`), имена перемешаны детерминированно. RAW-содержимое не нужно:
  `scan_folder` читает только имена и `symlink_metadata` на каждый entry.
- Замеряется production-функция `scan_folder` без изменений; рядом —
  инструментированная реплика, разделяющая фазы `enumerate+stat` и
  `sort_by_cached_key`. Реплика на каждой итерации ассертит побайтовое
  равенство результата с production.
- 3 warm-up + 30 итераций (1k) / 10 итераций (10k), p50/p95/max.
- «Quasi-cold» — первый прогон сразу после создания файлов. Это **не**
  настоящий cold: сбросить page cache на macOS без root нельзя, а создание
  файлов само прогревает dentry/inode-кэш. Отмечено как верхняя оценка-намёк.
- Время до первого кадра моделируется аддитивно: `scan_folder` выполняется
  внутри обработчика событий winit на UI-потоке, поэтому первый кадр после
  drop папки задержан минимум на полное wall-time сканирования.

### Машина

Apple M5 (arm64), 24 GB RAM, macOS 27.0 (Darwin 27.0.0), встроенный NVMe.
`rustc` из rust-toolchain проекта, профиль `bench` (release, thin LTO).

## Вердикт

**Гипотеза опровергнута** на этой машине (warm, локальный NVMe):

- 1k: warm p95 = 3.9–10.1 мс — гейт 100 мс выполнен с запасом ~10–25×.
- 10k (формального гейта нет, сравниваем с теми же 100 мс): warm p95 =
  48–93 мс — в среднем вдвое ниже гейта, но один из прогонов дал p95 = 93.2 мс,
  т.е. запас по гейту на 10k невелик и зависит от состояния VFS-кэша.

Оговорки:

1. **Cold-гейт 250 мс не измерен** — сброс page cache недоступен без root;
   quasi-cold после создания файлов фактически тёплый. На реальном cold
   (только что примонтированная карта/сетевая папка) 10k записей — это 12.5k
   `symlink_metadata`, и гейт 250 мс, вероятно, будет под угрозой.
2. **Бюджет кадра нарушается уже сейчас**: 10k warm p50 ≈ 42–53 мс — это
   ~3 пропущенных кадра при 60 fps, хотя формальный гейт 100 мс выполняется.
   Гейт устойчивости `p95 ≤16.7 ms` для интерактива синхронный вызов не
   выполняет по определению.
3. Измерение — synthetic names-only; реальные фото-папки на HDD/NAS/SD будут
   медленнее, раскладка по фазам сохранится (stat-bound).

## Что дальше (минимальный вариант исправления, не реализовано)

Если гейт нужно гарантировать и на 10k/cold:

1. Увести `scan_folder` с UI-потока в фоновый поток (по образцу уже
   существующего `RawPrefetcher`/`Prefetcher` в `gallery.rs`):
   `open_dropped_path` публикует статус «scanning…» и возвращается
   немедленно — первый кадр не задерживается вообще.
2. Инкрементальная выдача: фоновый сканер шлёт батчи `Vec<PathBuf>`
   (например, по 256 записей) через bounded channel; `GalleryModel`
   дозаполняется чанками, первая строка каталога появляется после первого
   батча (~первые 256 stat'ов), а не после полного сканирования.
3. Отсортированный порядок сохранить через отложенную финальную сортировку
   или вставку с поддержанием порядка; генерация (`generation` token) для
   отмены при повторном drop — механизм уже есть в prefetch-инфраструктуре.

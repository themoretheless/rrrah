# Эксперимент C — GPU upload: параметризация tile_size/halo и полный дамп GpuUploadTimings

Дата: 2026-07-23. Исполнитель: Исполнитель_C. Зона: `crates/rrrah-gpu/**`.

## Follow-up 2026-07-25

Контрбалансированный 16× AB/BA rerun на актуальном row-wise packer подтвердил,
что фиксированный aligned default 1022 регрессирует на `4096×3072`: CPU upload
`35.63 vs 30.88 ms`, completion wall `52.95 vs 42.84 ms` для legacy 4096.

Planner сделан адаптивным: aligned 1022 остаётся базой, но один frame-sized tile
выбирается, когда помещается и уменьшает atlas минимум на 12.5%. После правки:

- `2048×1536`: tile 2048, completion p50 `8.69 vs 23.74 ms` (2.73×);
- `4096×3072`: оба пути tile 4096, CPU p50 `21.51 vs 21.27 ms` (паритет);
- `6240×4160`: tile 1022 сохранён, `61.65 vs 107.22 ms` (1.74×);
- `8192×6144`: направление остаётся шумным; policy для него не менялась.

Режим воспроизводится через `RRRAH_GPU_UPLOAD_AB=1`; после каждого upload
ожидается конкретный submission.

## Гипотезы

1. **H1**: фиксированная стоимость upload (валидация, планирование, аллокация текстуры, per-tile overhead `write_texture`) доминирует над per-byte стоимостью (упаковка halo/строк, копирование байтов).
2. **H2**: `tile_size = 4094/4096` выбран эвристически и не обязательно оптимален.

## Метод

- Железо: **Apple M5, Metal** (headless, `WGPU_BACKEND=metal`), `max_texture_dimension_2d=32768`, `max_texture_array_layers=2048`.
- Харнесс: `examples/gpu_smoke.rs` расширен:
  - обычный режим теперь печатает **все** поля `GpuUploadTimings` (validate/atlas_plan/texture_allocate/halo_pack/row_pack/write_enqueue/uniform_write/bind/total) в CSV;
  - tiling параметризован через env `RRRAH_GPU_TILE_SIZE` / `RRRAH_GPU_TILE_HALO` (дефолты библиотеки не изменены);
  - новый sweep-режим `RRRAH_GPU_SWEEP=1` (`RRRAH_GPU_SWEEP_REPS=n`): матрица RAW-размеров {2048×1536 (6 MB), 4096×3072 (25 MB), 6240×4160 (52 MB), 8192×6144 (100 MB)} × tile_size {default, 256, 512, 1024, 2048, 4096} × halo {0, 1, 2, 4}, 7–11 полных upload на конфигурацию, на конфигурацию выводится p50 каждой фазы + min total.
- В библиотеке: чистая функция `plan_tiling()` (unit-тестируемая без GPU), публичные `TilingOverrides` и `RawRenderer::upload_mosaic_with_tiling()`; `upload_mosaic()` делегирует с дефолтами. Дефолт: `halo=1`, `tile_size = min(max_texture_dimension_2d − 2·halo, 4096)` (на адаптерах с лимитом 4096 даёт ровно 4094 — отсюда «эвристика 4094»).
- Прогоны: 6 sweep-прогонов (3×7 reps + 3×11 reps) + обычный режим. Release build.
- **Ограничение измерений**: во время прогонов машина была под фоновой нагрузкой (параллельные cargo-сборки других задач), разброс между прогонами до 2–4×. Поэтому для сравнения конфигураций используется **min total по всем reps** (контеншн только добавляет время, min — робастная оценка стоимости без помех) и фазы из наименее зашумлённого прогона. Сырые CSV: `C_sweep_run1.csv`, `C_sweep_run2.csv`, `C_normal.csv` рядом с этим отчётом.

### Декомпозиция фаз (лучший прогон, 8192×6144, tile 1024, halo 1)

## Вердикты

### H1 (фиксированная стоимость доминирует) — **опровергнута**

- Константные фазы (validate, atlas_plan, texture_allocate, uniform_write, bind) суммарно **< 0.5 мс** на любом размере кадра — это < 1 % от total. `texture_allocate` не растёт с размером атласа (0.01–0.09 мс): Metal лениво коммитит страницы.
- Per-tile фиксированная стоимость мала: на 8192×6144 при переходе 48→12 тайлов (tile 1024→2048) total *растёт* (81→107 мс), а не падает; на 4096×3072 при 48→12 тайлов экономия ≈ 2.5 мс / 36 тайлов ≈ **0.07 мс на тайл**. Оценка per-tile fixed ≈ 0.05–0.15 мс — на два порядка меньше per-byte составляющей.
- Total масштабируется с **обработанными байтами** (площадь тайлов с halo + row-padding + staging copy), а не с числом тайлов: ~0.8–1.2 мс на MB атласа. Доминируют `halo_pack` (per-sample gather с saturating-арифметикой, ~55–65 %) и `write_enqueue` (staging memcpy, ~20–25 %).

### H2 (tile_size=4096 эвристичен) — **подтверждена; дефолт субоптимален**

- Для кадров меньше тайла дефолт катастрофичен: 2048×1536 упаковывается в тайл 4098² (33.6 MB работы при 6 MB кадра) → 18.2 мс против **3.5 мс** при tile 512 (**5.2× быстрее**). `tile_with_halo` всегда заполняет полный extent.
- Для больших кадров оптимум тоже не 4096: tile 1024–2048 быстрее на всех размерах ≥ 25 MB (на 100 MB: 81 vs 124 мс, **−35 %**). Маленькие тайлы (256) проигрывают per-tile overhead'ом и упираются в лимит 2048 слоёв на ≥ 50 MP.
- Наблюдаемый оптимум на M5: **tile_size ≈ 1024 при halo 1**; для кадров, умещающихся в один тайл, тайл должен подстраиваться под размер кадра.
- Побочный эффект: `row_pack` обнуляется, когда питч строки кратен 256 B (halo=0, tile 1024 → строки 2048 B). При halo ≥ 1 extent = 1026 → паддинг-копия 3–17 мс (5–15 % total). Подбор `tile_size + 2·halo` кратным 128 сэмплам (напр. tile 1022 + halo 1 → extent 1024) убирает эту копию без потери halo.

## Что дальше (не реализовано, за пределами задачи)

1. Адаптивный дефолт: `tile_size = min(1024, next_multiple(frame_dim))` либо single-tile путь для кадров ≤ лимита текстуры без halo-перепаковки полного extent — главный выигрыш (до 5× на кадрах ≤ 12 MP).
2. Выравнивание extent под `COPY_BYTES_PER_ROW_ALIGNMENT` (256 B) при выборе tile_size — убирает padded row copy.
3. Ускорение `tile_with_halo` (row-wise `copy_from_slice` вместо per-sample saturating gather) — это самая горячая фаза (~60 %).
4. `GpuUploadTimings` стоит пробросить в телеметрию приложения — сейчас полный дамп виден только в gpu_smoke.

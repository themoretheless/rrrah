# Эксперимент H — аналитическая разведка: feasibility GPU-декодинга CR3 entropy (Rice + MED) на wgpu compute

Исполнитель: Исполнитель_H. Аналитическая задача: **код не менялся**, зона записи — только этот файл.
Машина-контекст: Apple M5 (arm64), Metal через wgpu. Дата: 2026-07-24.

Вопрос пользователя: «Основное время — entropy decode (Rice + MED). Можно оптимизировать дальше через SIMD или GPU?»
Этот документ отвечает за часть GPU; SIMD — зона задачи G.

**Вердикт (кратко): нет, GPU-декодинг entropy-потока CR3/CRX для single-image latency не окупается и, что важнее, не имеет корректной параллельной схемы.** Поток внутри плоскости последователен в самой сильной форме: длина кода символа `n` зависит от *значений* всех предыдущих пикселей (см. §2), поэтому классическая двухпроходная схема «scan длин → параллельный decode» для CRX вырождается: pass 1 ≡ полный decode. Единственный честный GPU-вариант — 4 скалярных потока (по одному на плоскость), что даёт оценочно **0.3–0.7× от текущего CPU baseline 102 мс**, т.е. регрессию. Подробности и числа ниже.

## 1. Структура битстрима CR3/CRX (факты из кода)

Источники: `crates/rrrah-decode/src/cr3/crx.rs`, `lossless.rs`, `assemble.rs`, контракты `fixture_regression.rs`.

- **Контейнер**: один CRX sample на трек; 112-байтовый заголовок с явными байтовыми размерами плоскостей (маркеры FF02/FF03, `crx.rs:509-562`). Плоскости **байт-разграничены** — границы известны без декодирования.
- **4 независимые плоскости** R/G1/G2/B (`assemble.rs:1-8`): plane 0 = (even y, even x), и т.д. Каждая — отдельный непрерывный entropy-поток.
- **Один тайл на всё изображение**: `tile_width × tile_height = 6188×4120` = полный кадр (`crx.rs:728-729`, тест `parses_both_eos_r8_track_configurations`). **Слайсов и restart-маркеров внутри плоскости нет** — это подтверждается и поведением декодера: единый `FullEntropy` (reader + `rice_parameter` + `run_index`) живёт непрерывно через все 2060 строк плоскости (`lossless.rs:691-746`).
- **Профиль потока** (`lossless.rs:12-15`): `enc_type=0`, `levels=0`, один саббанд, 14 бит, EOS R8.
- **Формат символов** (`lossless.rs:553-649`):
  - адаптивный Rice: унарный quotient + `k` бит remainder; `k` адаптируется **по значению** декодированного символа после каждого сэмпла (`update_rice_parameter`, `lossless.rs:612-620`: пороги quotient>2 / quotient>5 вверх, нижний порог вниз, ±2 max за символ, clamp 0..=15);
  - escape: префикс из 41 нуля + 21 бит (`FULL_ESCAPE_PREFIX`/`FULL_ESCAPE_BITS`, `lossless.rs:32-33`);
  - run-режим: экспоненциальный код длины серии через `RUN_INDEX_TABLE` (`lossless.rs:37-39, 622-648`), вход в режим — по биту-флагу;
  - 8-байтовый префикс плоскости с первым сэмплом (`decode_first_row`, `lossless.rs:462-533`).
- **Предиктор**: MED (median of left/above/upper_left, `lossless.rs:1014-1016`) плюс контекстная коррекция символа для адаптации `k` по `above_right − above` (`adjusted_context_symbol`, `lossless.rs:1018-1021`).

Размеры (фикстура IMG_9043, из контракта `fixture_regression.rs:56-59`):
- плоскость: 3094×2060 = 6 373 640 сэмплов; всего 25 494 560 сэмплов (25.5 MP);
- сжатые плоскости: 4 631 608 + 4 978 552 + 4 977 664 + 4 681 312 = **19 269 136 B** ≈ 19.3 MB → ~6.05 бит/сэмпл;
- распакованная мозаика: 25.5M × 2 B ≈ **51 MB**.

CPU baseline (sweep `RRRAH_CR3_PLANE_WORKERS`, M5, по данным оркестратора / `docs/experiments/B.md`):
1 worker → 309 мс; 2 → 168 мс; 4 (streaming) → **102 мс** plane_wall; полный decode ~120 мс.
То есть агрегатно ~4.0 нс/сэмпл wall, ~16 нс/сэмпл на одного plane-воркера (~50–60 тактов/сэмпл на ядро).

## 2. Последовательные зависимости — точный инвентарь

Внутри одной плоскости есть **три** вложенные последовательные зависимости, и две из них — по *значениям*, а не по длинам:

1. **Позиция в битстриме**: VLC — позиция символа `n` = сумма длин всех предыдущих. Стандартно для entropy-кодов.
2. **Адаптивный параметр Rice `k`**: `k_n` — функция от *декодированных значений* всех предыдущих символов (`update_rice_parameter`). Значит, даже **длину** символа `n` нельзя узнать, не декодировав значения `0..n−1` (remainder входит в mapped value, от которого адаптируется `k`).
3. **Run-режим зависит от реконструированных пикселей**: вход в run-ветку — это условие на *значения предикторов*:
   - верхняя строка: `predictor == 0` (`lossless.rs:822`);
   - контекстные строки: `left == above && left == above_right` (`lossless.rs:925`).
   То есть **сам факт наличия/отсутствия run-бита и run-кода в потоке** — функция от реконструированного изображения. MED-предиктор, в свою очередь, требует `left` (текущая строка) и `above`/`upper_left`/`above_right` (предыдущая строка).

**Ключевое следствие (убивает двухпроходную схему).** Классический GPU-паттерн для VLC — pass 1: лёгкий scan, считающий только *длины* кодов для построения таблицы offsets; pass 2: массово-параллельный decode по известным offsets (подход Sodsong et al. и nvCOMP-style chunking). Для CRX «length-only scan» **не существует**: из-за пунктов 2–3 длины зависят от значений и от реконструкции пикселей. Pass 1 обязан выполнять полный Rice-decode + полный MED + run-логику — то есть это и есть весь декодер, минус запись выхода (экономия ~10–20 %, не больше). Параллелизировать сам pass 1 нельзя по той же причине. **Круговая зависимость не разрывается.**

Единственные точки синхронизации в формате — **начала 4 плоскостей**. Это 4-way параллелизм, уже полностью занятый четырьмя CPU-воркерами streaming-планировщика.

## 3. Подходы из литературы и их применимость к CRX

| Подход | Источник | Почему работает там | Применимость к CRX |
|---|---|---|---|
| Self-synchronizing brute-force: поток на каждый бит-offset, отбраковка ложных синхронизаций | Weißenberger & Schmidt, «Accelerating JPEG Decompression on GPUs», 2021 (arXiv:2111.09219): до 51× vs libjpeg-turbo, 8× vs nvJPEG на A100 | **Статические** таблицы Хаффмана + маркеры EOB; ложная синхронизация быстро расходится и отбраковывается | **Не работает.** (а) Код не статичен: `k` адаптируется по значениям — ложный старт декодирует «правдоподобные» остатки из той же битовой смеси, и `k` сходится к похожей траектории *статистически*, но не *точно* → позиции дрейфуют, точной ресинхронизации нет. (б) Run-биты зависят от пикселей — ложная ветка не обязана быстро самоубиваться. (в) Lossless-вьюверу нужна гарантия bit-exact, а не вероятностная сшивка. |
| Row-index table + волновая реконструкция предиктора | Bernard & Marcus (ZITI Heidelberg, Annual Report 2008–2010): GPU lossless JPEG, 15–30× vs CPU | Таблица offsets **добавлена энкодером** (FPGA), строки независимы; MED-подобный предиктор реконструируется wavefront'ом | Формат CR3 фиксирован Canon — индекса строк **нет** и не будет. Сама волновая реконструкция (анти-диагонали 3094-широкой плоскости — тысячи независимых пикселей на фронт) была бы на GPU отличной, но она недостижима: упирается в последовательный entropy. |
| Chunk-parallel by design (nvCOMP ANS/GDeflate/Bitcomp, DietGPU rANS) | docs.nvidia.com/cuda/nvcomp; github.com/facebookresearch/dietgpu (250–410 GB/s decode на A100) | Форматы нарезают данные на независимые чанки **при сжатии**; каждый чанк — свой workgroup | Это свойство формата, а не декодера. CR3 — один непрерывный поток на плоскость. Вывод литературы как раз подтверждает наш вердикт: скорость GPU-кодеков покупается дизайном формата. |
| Host-прес scan границ (Sodsong et al.), прескан на CPU | цит. по arXiv:2111.09219, Related Work | Скан длин дешевле полного decode для JPEG | Для CRX scan ≡ полный decode (§2), смысл исчезает. |
| Restart markers / слайсы (GPUJPEG, Canon **CR2** lossless JPEG) | GPUJPEG; CR2 имеет слайсы с независимыми JPEG-LS-подобными потоками | Точки ресинхронизации в формате | В CR3 их нет. **Важно для роадмапа**: если rrrah будет декодировать CR2 — там GPU/многопоточность по слайсам честно доступны. |

Отдельно: аппаратные блоки (Apple VideoToolbox, NVIDIA NVDEC/nvJPEG) CR3/CRX не поддерживают; nvCOMP — CUDA-only, для wgpu/Metal недоступен и всё равно не про чужой формат.

## 4. Практическая оценка на wgpu/Metal (M5)

### 4.1. Ограничения WGSL/wgpu

- WGSL **не имеет 64-битных целых**: резервуар `MsbBitReader` (u64, `lossless.rs:213-390`) эмулируется парой u32 — каждый refill/consume удваивает число операций и веток. `countLeadingZeros` есть, но fused Rice fast-path (`lossless.rs:569-597`) придётся переписывать на двухсловную арифметику.
- Нет динамической памяти; workgroup-память 16–32 KB; буфер строки (3094+2)×i32×2 ≈ 25 KB — впритык, жить можно, но только в storage.
- Скалярная производительность одного GPU-потока на Apple GPU заметно ниже CPU-ядра (пропускная архитектура: нет больших кэшей и branch predictor'ов уровня CPU, частота ниже): честная оценка **0.3–0.5×** от одного CPU-ядра на ветвистом последовательном коде. А наш hot loop — это именно ветвистый код с data-dependent ветками (run-флаг, escape, адаптация).

### 4.2. Трансферы (калибровка по `docs/experiments/C.md`)

Из C.md: на unified memory `device.poll` после enqueue ≈ 0.005–0.014 мс, копия почти мгновенная; вся стоимость — CPU-side упаковка. Для storage buffer (не текстурный атлас с halo_pack) стоимость близка к `write_enqueue` ≈ 0.15–0.25 мс/MB:

- upload битстрима 19.3 MB ≈ **3–5 мс**;
- readback мозаики 51 MB ≈ **8–13 мс** (если мозаика дальше идёт в текстуру рендера — часть readback'а была бы «бесплатной», но текущий CPU-путь тоже отдаёт её в GPU-пайплайн, так что это не выигрыш GPU-декодера);
- фиксированные dispatch/pipeline ≈ 0.1–0.3 мс.

Трансферы — **не главная** проблема (~12–18 мс), но и не ноль: это уже 12–18 % от CPU baseline.

### 4.3. Вариант A: «честный» GPU-декодер — 4 скалярных потока

Единственная корректная схема: 4 workgroup × 1 поток, каждый последовательно декодирует свою плоскость (порт `decode_plane_rows` на WGSL с двухсловным резервуаром).

- Самая длинная плоскость ≈ 77–80 мс на одном CPU-ядре (из sweep: 1-worker wall 309 мс / 4 плоскости).
- GPU-поток при 0.3–0.5× скалярной скорости → **160–270 мс** на плоскость; wall = max по плоскостям + трансферы ≈ **170–285 мс** против **102 мс** CPU (4 потока).
- Утилизация GPU: 4 потока из ~десятков тысяч доступных → ~0.01 %. Энергия и площадь GPU потрачены впустую, при этом GPU нужен рендеру.

**Оценка: 0.35–0.6× от CPU baseline. Регрессия.**

### 4.4. Вариант B: brute-force self-sync (по Weißenberger)

- Усиление работы: поток на бит-offset × K символов на попытку — на ~2 порядка больше работы, чем сам decode; на 160 Мбит это ~10⁹–10¹⁰ пробных символов.
- Даже при бесконечном GPU это **не даёт корректного результата** для адаптивного Rice (§3): точной ресинхронизации нет, lossless-контракт (`fixture_regression` сверяет пиксели bit-identical) не выполняется.
- **Отклонён по корректности, до вопроса о скорости.**

### 4.5. Вариант C: двухпроходный scan+decode

Невозможен конструктивно: pass 1 ≡ полный decode (§2). **Отклонён.**

### 4.6. Вариант D: гибрид — CPU decode прямо в GPU-mapped буфер

Не GPU-декодинг, а оптимизация стыковки: писать распакованные плоскости/мозаику сразу в buffer, читаемый GPU (на unified memory — zero-copy). Это убирает часть readback/upload в *существующем* пайплайне и не требует GPU entropy-декодера. Отнести в зону rrrah-gpu (владелец F), здесь только фиксирую как единственный разумный «GPU-выигрыш» вокруг decode.

### 4.7. Сводная оценка

| Схема | Оценка wall | vs CPU 102 мс | Корректность |
|---|---|---|---|
| A: 4 скалярных GPU-потока | 170–285 мс | 0.35–0.6× | bit-exact возможна |
| B: brute-force self-sync | н/д | н/д | **нет** (адаптивный k) |
| C: 2-pass scan+decode | невозможен | — | — |
| D: CPU decode → GPU-mapped выход | ~102 мс − часть трансферов | ~1.0–1.1× | bit-exact |

Честный диапазон speedup GPU entropy decode: **0.3–0.7× (отрицательный)**; при самых щедрых допущениях (GPU-поток = 0.7× CPU, трансферы zero) — в лучшем случае паритет, который не оправдывает второй реализации декодера.

## 5. Вердикт

1. **GPU-декодинг CR3 entropy для single-image viewer latency — не окупается и не имеет корректной массово-параллельной схемы.** Причина фундаментальная, не инженерная: формат хранит 4 непрерывных потока без restart-точек, а длины кодов зависят от реконструированных значений (адаптивный k + run-условия на пикселях). 4-way параллелизм плоскостей уже исчерпан CPU.
2. **Batch-нагрузка вердикт не меняет**: несколько изображений тривиально параллелятся по изображениям на 8–10 CPU-ядрах; GPU снова остаётся с 4 скалярными потоками на кадр.
3. **Дизайн-эскиз «если бы пришлось»** — вариант A (§4.3): WGSL-ядро, 4 workgroup × 1 thread, двухсловный (u32×2) 64-битный резервуар, строка коэффициентов в storage buffer (~25 KB), построчный emit в mosaic buffer, run/Rice/escape-логика портируется 1:1 из `lossless.rs`. Ожидание: 0.35–0.6× от CPU. **Реализовывать не рекомендуется** — документировать как отклонённый.
4. **Когда пересматривать**:
   - CR2/JPEG-LS-подобные форматы со слайсами/restart markers — там slice-parallel decode на GPU доказан (15–30× в литературе); это уже другая задача и другой формат;
   - если появится собственный формат кэша превью — проектировать его chunk-parallel сразу (по образцу nvCOMP/GDeflate);
   - гибрид D (§4.6): decode в GPU-mapped буфер — единственная практически полезная GPU-смежная оптимизация, в зоне rrrah-gpu.
5. **Риски гипотетической реализации** (для полноты): отсутствие u64 в WGSL; ветвистый data-dependent код → дивергенция/скалярность; вторая реализация декодера = вторая база для bit-identical регрессий на всех GPU-бэкендах (Metal/Vulkan/DX12); время компиляции шейдеров в критическом пути открытия файла; поддержка escape/run-угловых случаев дважды.
6. **Куда смотреть вместо GPU**: CPU-оптимизации hot path (задача G): u128-резервуар, multi-symbol-per-refill, batch emit; теоретический потолок SIMD ограничен последовательным MED вдоль строки (автовекторизация возможна только для emit/record-этапов). Это дешевле, bit-exact проверяется существующей регрессией и не требует второй реализации.

# Отдельный процесс LoFTR

`model_worker::proposals_from_worker` доступен с feature `decode`. Он подходит
как поставщик предложений для `model_compare::compare_model_files_with`.
Декодирование, проверки исходных файлов, геометрия и подтверждение оригинальными
пикселями остаются в родителе. В дочерний процесс переносится вывод модели.

Сборка исполнителя требует настроенного окружения libtorch:

```sh
cargo build -p rrrah-dedup --features loftr --bin rrrah-loftr-worker
```

Вызывающая сторона задаёт доверенный путь исполнителя, веса и `ModelWorkerPolicy`:
дедлайн, интервал опроса, ограничения входа/выхода, максимальное число пикселей
одного изображения и предложений, число потоков и seed. Для двух изображений
по 640×640 необходим вход не менее `48 + 2 * 409600` байт. Для 5000 предложений
лимит stdout должен составлять не менее `16 + 40 * 5000` байт. Лимит stderr
должен быть ненулевым. Родитель резервирует управляемый бюджет для запроса,
максимального захвата вывода и возвращаемых предложений.

Callback настройки `Command` позволяет явно передать окружение загрузчика
библиотек дочернему процессу. На macOS контрольный стенд передаёт
`DYLD_LIBRARY_PATH` именно через этот callback: окружение запуска Cargo может
отличаться от окружения отдельного исполнителя. stdout зарезервирован для
двоичного протокола; диагностические сообщения должны идти в stderr.

Ошибка запуска, ненулевой exit, отмена, дедлайн, превышение лимита и некорректный
протокол возвращаются как ошибки. Их нельзя заменять пустым списком предложений
или отрицательным решением о дубликате. Корректный ответ с нулевым числом
предложений разрешён, но сам по себе не доказывает отсутствие совпадения.

Ненулевой exit представлен `ModelWorkerError::WorkerFailed { status, stderr }`.
Диагностика хранится в управляемом `SharedBuffer<u8>` вместе с консервативным
резервом захвата. Если вызывающая сторона сохраняет ошибку или клонирует её
`stderr`, этот резерв остаётся занят до освобождения последнего владельца.
Остальные остановки процесса представлены `ModelWorkerError::Worker`.

Исполнитель одноразовый: каждый вызов запускает процесс и загружает модель.
Повторное использование модели между банками пока отсутствует. Ограничения
протокола и `MemoryBudget` не ограничивают RSS тензоров Torch. Жёсткий RSS-лимит,
контроль потомков и гарантированное время остановки активного kernel ещё не
квалифицированы. Существующие API `model_loftr` остаются внутрипроцессными.

Аудит протокола и трёх реальных сравнительных контролей:
`research/dedup-model-worker-audit-20261013.json`. Это проверка сохранения
результатов при переносе вычисления, а не оценка полноты поиска на всём корпусе.
